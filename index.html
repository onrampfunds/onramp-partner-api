Onramp Funds Partner API (1.2.0)

Download OpenAPI specification:

Overview

The Onramp Funds Partner API enables partners to submit referrals for business funding and receive prequalification amounts. This REST API uses JWT authentication and provides a streamlined workflow for processing funding applications.

Who Is This API For?

This API is designed for Onramp partners who want to:

  • Submit seller referrals programmatically
  • Receive instant prequalification amounts
  • Integrate Onramp funding into their platform

Getting Started

Prerequisites

Before using the API, you need:

  1. Partner Account - Register with Onramp Funds as a partner
  2. API Credentials - You'll receive a client_id and client_secret
  3. HTTPS Support - All API calls must be made over HTTPS

Base URL

https://app.onrampfunds.com/

Authentication

The API uses JWT (JSON Web Token) authentication. You must obtain a token before making API calls.

How Authentication Works

  1. Obtain Credentials - Receive your client_id and client_secret from Onramp
  2. Generate Token - Use the /partners/api/tokens endpoint to get a JWT token
  3. Use Token - Include the token in the Authorization header for subsequent requests

Token Generation Example

curl -X POST https://app.onrampfunds.com/partners/api/tokens \
  -H "Content-Type: application/json" \
  -d '{
    "client_id": "YOUR_CLIENT_ID",
    "client_secret": "YOUR_CLIENT_SECRET"
  }'

Response:

{
  "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "token_type": "Bearer",
  "expires_in": 3600,
  "expires_at": 1770000000
}

expires_in is a duration in seconds (per OAuth convention); expires_at is the same expiry as an absolute Unix timestamp. Use whichever your HTTP library expects, and refresh on a 401 either way.

Using Your Token

Include the token in the Authorization header for authenticated endpoints:

Authorization: Bearer YOUR_JWT_TOKEN

Important: Store your credentials securely. Never expose them in client-side code or public repositories.

API Workflow

There are two ways to integrate. They are separate paths, not steps in one flow:

  • Referral hand-over — POST /partners/api/referrals. Your server submits a seller's details and receives a prequalified amount plus a referral URL to send them to. This is the workflow described below.
  • Embedded card — GET /partners/api/embed/prequalifications. Returns the configuration that @onrampfunds/embed renders directly in your own page, so the merchant sees their amount without leaving it. Three required parameters plus an optional business name, and none of the sensitive applicant data the referral path collects.

The steps that follow describe the referral hand-over. For the card, see GET /partners/api/embed/prequalifications below.

Step-by-Step Guide

Step 1: Generate Authentication Token

Make a POST request to /partners/api/tokens with your credentials.

Step 2: Create a Referral

Submit referral details to /partners/api/referrals with the following information:

  • Seller email and business details
  • Legal entity information
  • Platform sales data (e.g., Shopify, Amazon)
  • Optional: Additional business details for enhanced prequalification

Step 3: Receive Prequalification

The API responds with:

  • Prequalified funding amount
  • Correlation ID for tracking
  • Referral URL for the seller
  • Submitted referral details

Complete Example

# Step 1: Get token
TOKEN=$(curl -X POST https://app.onrampfunds.com/partners/api/tokens \
  -H "Content-Type: application/json" \
  -d '{
    "client_id": "YOUR_CLIENT_ID",
    "client_secret": "YOUR_CLIENT_SECRET"
  }' | jq -r '.access_token')

# Step 2: Create referral (minimal example)
curl -X POST https://app.onrampfunds.com/partners/api/referrals \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $TOKEN" \
  -d '{
    "seller_email": "seller@example.com",
    "business_name": "Example Business Inc",
    "seller_tenure_months": "24",
    "legal_entity": "llc",
    "incorporation_state": "CA",
    "platforms": [{
      "type": "shopify",
      "seller_id": "shop_12345",
      "sales": {
        "90_days": 45000.00
      }
    }]
  }'

Response:

{
  "business_name": "Example Business Inc",
  "legal_entity": "llc",
  "incorporation_state": "CA",
  "prequalified_amount": 23000.00,
  "referral_url": "https://app.onrampfunds.com/partners/referrals/...",
  "correlation_id": "065a417b-ce17-4c64-b8dd-e35a3128a021"
}

The amount follows from the 90-day sales total in the request: 50% of $45,000 is $22,500, rounded up to the nearest $1,000.

Using the Referral URL

Once you receive the response, you need to direct the seller to the referral_url to complete their funding application. You can do this in two ways:

Option 1: Redirect the User

// Redirect the user immediately after receiving the response
window.location.href = response.referral_url;

Option 2: Provide a Link

<!-- Display a link for the user to click -->
<a href="https://app.onrampfunds.com/partners/referrals/...">
  Continue to complete your funding application
</a>

The referral URL is a unique, personalized link for each seller that:

  • Contains their pre-filled information
  • Shows their prequalified amount
  • Guides them through the funding application process
  • Tracks the referral back to your partner account

Required vs Optional Fields

Minimum Required Fields

To create a referral, you only need to provide:

  • seller_email - The seller's email address

Recommended Fields for Better Prequalification

For more accurate prequalification amounts, include:

  • business_name - Business name
  • seller_tenure_months - How long the business has been operating
  • legal_entity - Legal structure (sole_proprietorship, partnership, corporation, llc)
  • incorporation_state - State of incorporation
  • platforms - Sales data from e-commerce platforms

Enhanced Fields

For the most comprehensive prequalification and faster processing, consider including:

  • Business identification (EIN, registered business name, SOS filing number)
  • Operating and mailing addresses
  • Controller information (title, DOB, identification)
  • Industry classification
  • Desired funding amount and planned use of funds

Sales Data Format

The sales object on a platform carries that channel's sales in one of three representations:

Representation Keys How it is read
90-day total 90_days Used as given
180-day total 180_days Halved, as a 90-day proxy
Monthly series YYYYMM Three most recent months, summed

Send one representation per platform. They are alternatives, not inputs to be combined — see How Sales Are Aggregated below.

A 90-day total:

"sales": {
  "90_days": 45000.00
}

A monthly series:

"sales": {
  "202401": 12000.00,
  "202402": 15000.00,
  "202403": 18000.00
}

How Sales Are Aggregated

Each platform resolves to a single 90-day figure, and those figures are summed across platforms. Within one platform the first match wins, and the remaining keys are never read:

  1. 90_days — used as given
  2. otherwise 180_days — multiplied by 0.5, as a 90-day proxy
  3. otherwise the YYYYMM months — sorted newest first, the current month dropped, and the top three summed

Three consequences are worth stating outright, because each has a plausible reading that is wrong:

  • 180_days does not yield a larger amount. It is halved. If you hold both windows, send 90_days — sending the wider one produces an estimate from half of it.
  • Sending more than three months does not widen the window. Three are used; the rest are ignored. Twelve months of history and three months of history give the same answer.
  • The current month is always dropped, since it is still partial. A series running to the current month contributes the three months before it.

Sending an aggregate and a series is accepted, but the series is dead weight — the aggregate wins and the months are never read. It does not make the estimate more accurate or more robust.

Platforms Onramp Does Not Recognise

A platform whose type is not recognised contributes zero, and nothing in the response says it was skipped. At least one platform must carry a recognised storefront type, or the request is rejected with a 422 — and that error lists the accepted values, which is the most reliable way to check a type you are unsure about.

A request that clears that bar can still carry unrecognised platforms alongside the valid one, and those contribute nothing. So a 422 reading must report sales greater than 0 can arrive on a request that plainly contains sales: the message describes the total after unrecognised platforms are dropped, not the figures you sent. If you see it and your figures look right, check the type values first.

Request and Response Casing

Requests accept either case

Every endpoint accepts both snake_case and camelCase request keys and normalises them server-side. sellerEmail and seller_email are the same parameter, and mixing the two styles within a single request is allowed.

Sales period keys are not affected by this normalisation. Send 90_days, 180_days, and YYYYMM keys exactly as documented, whichever style you use for everything else.

Responses do not all use the same case

Response casing differs by endpoint. This is deliberate, not an oversight:

Endpoint Response case
POST /partners/api/tokens snake_case
POST /partners/api/referrals snake_case
GET /partners/api/embed/prequalifications camelCase

Each response matches its consumer. The token and referral responses are read by your server alongside the rest of this API, so they stay snake_case. The embed prequalification response is passed to @onrampfunds/embed's mount(), which expects camelCase — serving it in snake_case would oblige every partner to write the same key-mapping layer before forwarding it, and a mapping layer between a response and its only consumer is a place for the two to drift apart.

Error responses are always snake_case, on every endpoint, including the embed one. The errors object is keyed by parameter name in snake_case (for example seller_email) no matter which case you sent.

Error Handling

The API uses standard HTTP status codes and returns detailed error information.

Request IDs

Every response — success or error — carries an X-Request-Id header uniquely identifying that request. Log it alongside your own request records and quote it when contacting support: it lets Onramp find the exact request in server logs without any other identifying detail.

Common HTTP Status Codes

Status Code Meaning Action
200 Success Request processed successfully
201 Created Referral created successfully
400 Bad Request Check request format and data types
401 Unauthorized Verify credentials or token validity
422 Validation Error Review validation errors in response
500 Server Error Contact Onramp support if persists

Error Response Format

{
  "status": 422,
  "error": "validation_error",
  "message": "Validation failed",
  "errors": {
    "seller_email": ["can't be blank"],
    "legal_entity": ["is not included in the list"]
  }
}

Common Issues

401 Unauthorized

  • Token expired or invalid
  • Missing Authorization header
  • Invalid client credentials

422 Validation Error

  • Missing required fields
  • Invalid enum values (e.g., legal_entity, incorporation_state)
  • Improperly formatted data (email, SSN, EIN patterns)

Best Practices

Security

  • Store credentials securely - Use environment variables or secure vaults
  • Use HTTPS only - Never make requests over HTTP
  • Rotate secrets regularly - Contact Onramp to update credentials
  • Validate input - Sanitize data before sending to the API
  • Protect sensitive data - Handle SSNs, EINs, and personal information with care

Token Management

  • Cache tokens - Reuse tokens instead of generating new ones for each request
  • Handle expiration - Implement retry logic with token refresh on 401 errors
  • Monitor usage - Track API calls for debugging and optimization

Data Quality

  • Provide accurate sales data - More data leads to better prequalification
  • Use consistent formats - Follow the specified date and number formats
  • Include all platforms - Submit data for all relevant sales channels
  • Complete business information - More details enable faster processing

Error Recovery

  • Implement retries - Use exponential backoff for transient failures
  • Log errors - Maintain logs for troubleshooting
  • Validate before sending - Client-side validation reduces error rates

Prequalify a merchant for the embedded card

Returns the configuration consumed by the @onrampfunds/embed package's mount(). Forward the response body through unmodified: it is shaped for the card, and is not a general prequalification resource.

Three required parameters, plus an optional business_name. None of the sensitive applicant data the referral path collects appears here: that endpoint accepts EIN, SSNs and addresses, and this one neither asks for them nor returns them.

seller_email is personal data and should be handled as such, but it is the only such field, and no response echoes it back — even when the record found already holds a full referral payload.

Find-or-create, keyed on the seller's email

Requests are keyed on (your partner account, seller_email). The first call for a merchant creates the record; every later call returns that same record and the same correlationId. Repeat calls are the expected pattern rather than an error — the card renders on every page load, and each render is counted.

Responses are camelCase

Unlike POST /partners/api/referrals, which responds in snake_case, this endpoint responds in camelCase so the body forwards into mount() without a key-mapping layer. Requests still accept either case. See Request and Response Casing above for why the two differ.

A 200 does not guarantee an amount

When amount is null the merchant cannot be served. This is a success, not an error: mount() returns null, renders nothing, and yields the slot back to your page, so you can lay out around its absence.

The no-amount response carries only correlationId, amount, currency, and lexicon. There is no applyUrl, copy, or theme, because nothing is rendered and so no regulated wording is owed.

Two situations produce it:

  • The merchant's operating_state is one Onramp does not operate in. lexicon is null in this case.
  • The merchant's 90-day sales fall below the qualifying threshold. lexicon is populated.

Missing or zero sales are a 422, not a null amount. The distinction is the point: answering null to a request that reported no sales would let a broken integration look indistinguishable from a merchant who genuinely does not qualify, and you would have no signal that anything was wrong.

How the amount is calculated

50% of the 90-day sales total, rounded up to the nearest $1,000, capped at $500,000. Merchants below $22,500 in 90-day sales receive the no-amount response rather than a floored figure.

See How Sales Are Aggregated above for how the 90-day total is derived when you send 180_days or monthly figures instead.

Caching

Every response carries Cache-Control: no-store, including rejected ones. The body holds a merchant-specific amount and regulated copy with no expiry field to bound its staleness, and each call is also recorded as an impression. A cached response therefore both shows a stale figure and silently drops renders from reporting. Do not cache it, and do not place it behind a proxy that ignores the header.

The merchant's sales channels and their reported sales. At least one platform with a recognised type is required, and the reported sales must total more than zero.

Nested parameters use Rails bracket notation in the query string. A single-platform request looks like:

GET /partners/api/embed/prequalifications
  ?seller_email=merchant%40example.com
  &operating_state=TX
  &platforms[][type]=shopify
  &platforms[][seller_id]=seller-1
  &platforms[][sales][90_days]=45000.0

The schema below is the parsed shape, not the wire format. Standard OpenAPI array serialization does not produce the form above, so a generated client will build the wrong URL unless you override it — emit the bracketed keys literally, repeating platforms[] once per platform.

Indexed keys are not an equivalent spelling. platforms[0][type]=shopify parses into an object keyed "0" rather than an array, and the request is rejected with a 422 reading platforms: must be an array of platform objects.
